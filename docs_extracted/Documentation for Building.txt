MVP generation language is Python, consistent with the iCoder experimental setup.
Direct empirical comparator is ChatDev; iCoder source code is unavailable.
Main comparison uses GPT-4o. The cheaper model is explicitly GPT-4o-mini.
For iCoder-style consistency, MAS uses the lightweight sentence-transformers model `all-MiniLM-L6-v2` as an implementation choice. This is not claimed to

DOCUMENT 1 — PRODUCT REQUIREMENTS DOCUMENT
1. Problem
LLM-based multi-agent software generation can improve system-level code generation through decomposition, architecture constraints and iterative review,
but these mechanisms can introduce substantial computational overhead. iCoder separates requirement analysis, architecture design, development and
quality assurance, and uses Sprints as the iterative control unit. Its RABot decomposes requirements and creates stories/Sprints; UMLBot creates
architectural views; DevBot generates code; ReviewBot performs dependency-aware review and testing. (iCoder, Secs. 3.1–3.3; Figs. 1–7.)
The research problem for MAS is: Can a multi-agent software-engineering workflow retain the quality benefits of structured development while reducing
unnecessary model calls, context size and iteration cost?

5. Concrete Router Decision Logic
The Router is deterministic and does not call an LLM. Each feature is a keyword/regex rule applied to the normalized requirement text. Multiple matches in
one feature count according to the rule below.
Threshold: score 0–3 → SIMPLE; score 4+ → STRUCTURED. A 10-task hand-labeled router-accuracy check is run separately and reports accuracy,
false-SIMPLE rate and false-STRUCTURED rate. The hand labels are fixed before evaluation.
Note: these deterministic features are a concrete MVP routing policy, not a claim that the iCoder paper used the same rules.
6. AST Review Pipeline
Changed .py files ↓ ast.parse() ↓ Import / ImportFrom extraction ↓ Module resolution ↓ Directed dependency graph ↓ Cycle detection ↓
Undefined/local-import checks ↓ Changed-module impact report
Structural checks are deterministic and do not consume model tokens. GPT-4o-mini is reserved for semantic/requirement review. This is an MVP
reinterpretation of iCoder's R-DCGG review role (Sec. 3.2.4).
7. Neutral Cross-System Quality Checks
iCoder-style completeness: proportion of implemented functions after the documented placeholder rule.
iCoder-style executability: successful execution/pass rate using the same evaluator environment.
iCoder-style consistency: cosine similarity between requirement and generated code embeddings using `all-MiniLM-L6-v2`; this is an MAS implementation
choice, not a claimed reproduction of iCoder's embedding model.
iCoder-style Quality: arithmetic mean of per-project Completeness × Executability × Consistency.
Ruff, Bandit and Radon are run with identical commands/settings on MAS and ChatDev outputs.
Shared fixed test method: a neutral black-box evaluator protocol is fixed before the comparison and applied identically to both systems. It may use
task-specific fixed inputs/expected outputs, but it never uses tests generated by either system.
MAS-generated pytest pass rate and coverage are collected separately as MAS-only diagnostics.
8. Adaptive Stopping Rule
The adaptive score is separate from the iCoder-style Quality metric. Default weights:
CE_t = 0.5 * (Completeness_t + Executability_t) S_t = 0.30*SharedTest_t + 0.10*Ruff_t + 0.15*Bandit_t + 0.10*Radon_t + 0.15*Reviewer_t + 0.20*CE_t ∆_t =
S_t - S_(t-1) Defaults: STOP_EPSILON = 0.02 PATIENCE = 2 MAX_ITERATIONS = 3
Stop when: (1) no critical defects and the shared fixed test passes; OR (2) ∆ remains below 0.02 for two consecutive iterations; OR (3) three iterations are
reached. All weights, STOP_EPSILON, PATIENCE and MAX_ITERATIONS are configurable in one versioned configuration file.

DOCUMENT 3 — SECURITY AND ACCESS SPECIFICATION
1. Security Objective
The MVP is local and single-user. It does not implement JWT login, roles, ownership checks, enterprise access control or multi-user audit identity. Security
focuses on protecting the host, secrets, execution environment and agent workflow.
2. Threat Model
3. Sandboxed Execution
`--network none`
1 CPU core
512 MB memory target
Limited PIDs
30–60 second execution timeout
Read-only base filesystem
Writable `/workspace` only
No host Docker socket
No host filesystem mounts except the isolated workspace
Disposable container per execution
External package installation is disabled during evaluation; dependencies come from a predefined evaluation image.
4. Prompt-Injection Handling
SYSTEM POLICY ↓ TASK METADATA ↓ USER REQUIREMENT ↓ AGENT INSTRUCTIONS
User requirements never override system instructions.
Agent artifacts are data, not instructions.
JSON artifacts are parsed structurally.
Tool calls are restricted to known application functions.
Generated code never receives API secrets.
Inter-agent communication uses structured conclusions rather than chain-of-thought.

5. Secret Handling
OPENAI_API_KEY= DATABASE_URL=
Store secrets in environment variables or a local secret file excluded by `.gitignore`.
Never write secrets to generated repositories, artifacts, logs or evaluation output.
Provide `.env.example`, not a committed `.env`.
Redact common key/token patterns from event summaries.
6. Access Model
MVP: single local user. No JWT, no roles, no ownership checks, no users table and no audit_logs table.
Future work: authentication, role-based access control, multi-user ownership and enterprise audit identity.
7. Append-Only Run Event Log
Record run_started, agent_started, agent_completed, artifact_rejected, rollback, code_executed, requirement_changed, evaluation_started and
evaluation_completed. Each event has a monotonic sequence number, run_id, event type, status, redacted summary and timestamp. Full prompts are not
logged by default.
8. Security Acceptance Criteria
Generated code cannot access the host.
Generated code cannot access the network.
Execution terminates on timeout/resource limits.
Model API keys never appear in generated files.
Invalid artifacts cannot directly control downstream agents.
Run events are append-only for the local execution history.
Authentication/roles are explicitly out of scope for the MVP.

Research Positioning
Recommended claim wording:
“MAS improves over ChatDev by X% on [metric], while addressing the computational-overhead limitation observed in iCoder; iCoder reported a Y% gain over
its baselines.”
Do not write: “MAS outperforms iCoder.” The comparison with iCoder is indirect and limited to the paper's reported results.
Published iCoder Reference Results
These values are published reference values, not MAS measurements. The paper reports 3%–7% quality improvements over baselines under GPT-3.5 Turbo
in its abstract and describes ablation evidence for iterative development, architecture, reverse dependency modeling and review.
Paper-to-MAS Design Rationale
Limitations
First, most SRDD tasks may route as SIMPLE under the deterministic Router, so the architectural contribution of UML/Sprint stages may be exercised less
frequently than in an always-structured system. Second, the comparison with iCoder is indirect: MAS does not reproduce iCoder and uses only the paper's
reported gains/results as reference. Third, the task set is small at 20 requirements for the main comparison, so statistical power and generalization are
limited. Fourth, consistency uses embedding similarity, which is a weak proxy for true requirement satisfaction and should not be interpreted as a complete
semantic correctness measure.
