# Benchmark Software-Generation Contract (v1.0 Frozen)

**Document Version:** 1.0.0-CONTRACT  
**Date of Freeze:** October 11, 2026  
**Status:** Canonical Experimental Specification  
**Applies To:** Multi-Agent Software Engineering Team (MAS) and ChatDev Baseline (`v1.0.0`)

---

## 1. Purpose & Scope

To guarantee a fair, symmetrical, and scientifically reproducible comparison between MAS, ChatDev, and the published iCoder reference benchmark (*Information and Software Technology*, 2026), both systems must generate software adhering to a single, identical software-generation contract.

Neither system shall receive special-case evaluation exceptions, relaxed constraints, or framework-specific accommodations.

---

## 2. Core Technical Specification

| Dimension | Specification | Verification Rule |
| :--- | :--- | :--- |
| **Target Language** | Python 3.11+ | All generated executable artifacts must be valid Python source code. |
| **Entry Point Convention** | `main.py` | Projects must provide a primary executable entry point (`main.py` or `app.py`) that initializes and runs the software. |
| **Interface Paradigms** | CLI or Headless-Compatible GUI (e.g., Tkinter) | If GUI is generated, it must initialize without requiring an interactive display and must terminate cleanly under headless test hooks. |
| **Dependency Policy** | Python Standard Library & Bundled Modules | Dependencies must not require external closed-source runtimes, unpinned system packages, or active internet connectivity during execution. |
| **Execution Sandbox** | Docker / Isolated Subprocess Sandbox | Strict bounds: `--cpus 1.0`, `--memory 512m`, `--pids-limit 64`, `--network none`, timeout 45s. |
| **Functional Completeness** | Concrete function implementation | $C_i = 1 - \frac{\text{unimplemented\_functions}}{\text{total\_functions}}$. Stubs (`pass`, `...`, `NotImplementedError`) penalize completeness. |
| **Execution Success Criteria**| Exit code 0, no unhandled exceptions | $E_i = 1.0$ only if entry point and behavior tests complete with exit code 0 under the 45s timeout. |
| **Specification Consistency** | Embedding similarity ($S_i \in [0.0, 1.0]$) | Cosine similarity between canonical requirement embedding and aggregate project code embedding (`all-MiniLM-L6-v2`). |
| **Primary Metric** | Multiplicative Quality ($Q_i$) | $Q_i = C_i \times E_i \times S_i$. |

---

## 3. Neutral Testing & Evaluator Symmetry

1. **Independent Test Harness:** All behavior tests are executed by `NeutralEvaluator` from outside both systems' workspaces. Tests are never supplied by or generated by the systems under evaluation.
2. **GUI / CLI Parity:**
   - GUI applications (e.g., Tkinter) are tested by constructing the application instance, initializing state, feeding test inputs, invoking solving routines, and verifying outputs.
   - CLI applications are tested by invoking the entry point with arguments/stdin or importing modular routines.
   - A smoke test passes only if essential module structures, widgets, or logic execute cleanly. Simply bypassing `mainloop()` without exercising module behavior is insufficient.
3. **Format Symmetry:** Projects are evaluated on functional behavior rather than rewarded or penalized merely for UI toolkit choices.
