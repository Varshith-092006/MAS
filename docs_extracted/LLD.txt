3.2 Class Descriptions
3.2.1 BaseAgent (abstract)
Purpose: The common base for all agents. It builds the prompt, calls the model and checks the
output.
Attributes:
• name: name of the agent
• llm: the LLM provider object
• validator: the schema validator
Methods:
• run(state): runs the agent and returns the updated state
• build_prompt(state): builds a small prompt from the state
14


--- PAGE 15 ---

3.2.2 ManagerAgent
Purpose: Cleans up the requirement and creates the state and the run record.
Attributes: config – settings of the run (model, seed, flags).
Methods:
• normalize(requirement): returns the TaskPlan
• init_run(config): creates the MASState
3.2.3 ComplexityRouter
Purpose: Decides SIMPLE or STRUCTURED using fixed rules. No model call.
Attributes:
• rules: list of (feature, regex) pairs
• threshold: score from which a task is STRUCTURED (default 4)
Methods:
• score(requirement): returns the score
• route(requirement): returns the label, the score and the matched features
3.2.4 ArchitectAgent
Purpose: Makes the small UML design and sprint plan for STRUCTURED tasks and gives the
needed UML part later.
Methods:
• design(state): returns the Architecture artifact
• slice_uml(files): returns the UML parts that matter for the given files
3.2.5 DeveloperAgent
Purpose: Writes the first code and the later patches from a small context.
Attributes: workspace – path of the project workspace.
Methods:
• generate(state): returns a CodePatch
• apply_patch(patch): writes the files and returns the list of changed files

3.2.6 TesterAgent
Purpose: Writes pytest tests and records the pass rate and the coverage for MAS’s own use.
Methods:
• generate_tests(state): creates the tests
• run_tests(): runs them in the sandbox and returns the TestReport
3.2.7 ReviewerAgent
Purpose: Checks the meaning of the code and the requirement match using GPT-4o-mini.
Methods: review(state) returns a ReviewReport with severity counts.
3.2.8 ReflectionAgent and AdaptiveStopper

4. Database Schema Design
MAS uses PostgreSQL to store runs, events, artifacts, checkpoints, model calls and metrics.
The generated source code is kept in the workspace and in Git. The database stores only
references to it. The tables are normalised, so every number in the evaluation can be traced
back to a run, a task, a system and its settings.
4.1 Entity Relationship Overview
The main entities are:
• tasks: the SRDD tasks
• evaluations: one benchmark or ablation batch
• runs: one execution of one system on one task
• agent_events: the event log, only new rows are added
• artifacts: outputs of the agents
• checkpoints: points to roll back to
• model_calls: token and cost log
• metrics: scores and diagnostics
• config_snapshots: record of the settings, for reproducibility

4.3 Indexes and Constraints
• Every child table has a foreign key to runs(run_id) with ON DELETE CASCADE.
• Index on agent_events(run_id, seq) to read events in order.
• Index on metrics(run_id, metric_name) and on runs(system, model, evaluation_id)
for quick results.
• The application role has no UPDATE or DELETE permission on agent_events, so it
only grows.
4.4 Design Decisions
• Scores are saved for every run and never overwritten. So the statistics can be calculated
again at any time.
• Neutral metrics (used to compare with ChatDev) and internal metrics (MAS only) are
kept apart using the scope column. So MAS pytest results never enter the comparison.
• Token counts come only from the usage fields of the provider, saved in model_calls.
• MAS is for a single user, so there is no users table and no audit table. Login is future
work.

7.2 AST Dependency and Cycle Detection
Purpose: To find circular imports and missing imports, and to find which modules are affected
by a change. No tokens are used.
function BUILD_GRAPH(files):
graph <- {}
for f in files:
tree <- ast.parse(read(f))
graph[module(f)] <- { resolve(imp) for imp in imports(tree) if internal(imp)
}
record unresolved imports of f
return graph
function FIND_CYCLES(graph):
color <- {v: WHITE for v in graph};
stack <- [];
cycles <- []
procedure DFS(u):
color[u] <- GRAY;
push(stack, u)
for v in graph[u]:
if color[v] == WHITE:
DFS(v)
else if color[v] == GRAY:
cycles.append(stack[index(v):] + [v])
pop(stack);
color[u] <- BLACK
for v in graph: if color[v] == WHITE: DFS(v)
return cycles
function IMPACT(graph, changed):
# modules that import the changed modules
reverse <- reverse_edges(graph)
return transitive_closure(reverse, changed)

7.4 Adaptive Score and Stopping Rule
Purpose: To stop the loop when another round is not worth its tokens. Only the signals inside
MAS are used. The neutral evaluator is never seen by the loop.
Each value below is between 0 and 1:
InternalTest = MAS pytest pass fraction (0 if no tests ran)
Ruff
= 1 - min(violations / 10, 1)
Bandit
= 1 - min((3*High + 2*Medium + 1*Low) / 10, 1)
Radon
= clip(mean maintainability index / 100, 0, 1)
Reviewer = 1 - min((3*critical + 1*major) / 6, 1)
CE
= 0.5 * (Completeness + Executability)
# internal smoke run
S_t = 0.30*InternalTest + 0.10*Ruff + 0.15*Bandit
+ 0.10*Radon + 0.15*Reviewer + 0.20*CE
function SHOULD_STOP(t, S, low_count, reports):
delta <- S[t] - S[t-1]
if no_critical(reports) and tests_pass(reports) and smoke_ok(reports):
return STOP("clean_result")
low_count <- low_count + 1 if delta < EPSILON else 0
# EPSILON = 0.02
if low_count >= PATIENCE:
return STOP("marginal_gain")
# PATIENCE = 2
if t >= MAX_ITERATIONS:
return STOP("max_iterations") # MAX = 3
return CONTINUE

7.5 Artifact Check, Retry and Rollback
function PRODUCE_VALID(producer, schema, state):
ref <- CHECKPOINT.save(state)
out <- producer(state)
errors <- VALIDATE(schema, out)
if errors is empty: return out
out <- producer(state, errors)
# retry once, showing the errors
if VALIDATE(schema, out) is empty: return out
CHECKPOINT.restore(ref);
log("rollback")
out <- producer(state)
# try again from the last good state
if VALIDATE(schema, out) is empty: return out
fail_run("artifact_invalid")

7.8 Paired Permutation Test
function PERMUTATION_TEST(a, b, trials = 10000):
# a, b: task-level means
d <- [a_i - b_i for each task i]
observed <- abs(mean(d))
count <- 0
repeat trials times:
flipped <- [s_i * d_i with s_i chosen randomly from {-1, +1}]
if abs(mean(flipped)) >= observed: count <- count + 1
return (count + 1) / (trials + 1)
# two-sided p-value

8.2 Communication Flows
1. Run execution: The API creates the run and the state. Then the flow is Manager, Router,
Architect (if needed), Developer, sandbox and tools, Reviewer and Reflection. Every step
creates an event that is saved and streamed.
2. Artifact exchange: Every agent gives a JSON artifact. The schema validator accepts or
rejects it before the next agent can read it. Agents share short structured results and not
their full reasoning.
3. Token counting: Every model call goes through the proxy. The usage fields are saved in
model_calls and added up per run, for both systems.
4. Evaluation: The runner collects the finished projects. The neutral evaluator, which the
agents cannot see, scores them and saves metrics with scope neutral. MAS-only checks
are saved with scope internal.
8.3 Error Handling and Logging
• Logging is central and uses Python logging. Secrets are removed from event summaries.

• Wrong artifacts: retry once, roll back, generate again, and then fail the run with a clear

8.4 Security Considerations
• MAS is a local single-user system. There is no login or role system in the MVP (future
work).
• Generated code runs only in Docker with no network, 1 CPU, 512 MB memory, limited
processes, a 30 to 60 second time limit, a read-only base filesystem and no host folders
except the workspace.
• Prompt injection control: system rules come first, then task data, then the user require-
ment (kept inside markers and not trusted), then the agent instructions. Artifacts are
treated as data and not as instructions.
• API keys come from environment variables or a file that Git ignores. We commit .env.example
and not .env.
• The generated code never gets any secret.

9.5 Extensibility
• New models: write a class for the LLMProvider interface and add the model name in the
settings.
• New tools: add a wrapper in the analysis folder and a rule to bring its value between 0
and 1 for the adaptive score.
• New programming languages: add an analyser for that language (future work).
• New ablations: add a feature flag and read it in the matching component.
9.6 Reproducibility and Seeds
• Fixed seed (42) for picking tasks and for the permutation tests. Temperature 0 for model
calls.
• Every run saves the model name and version, library versions, Docker image tag, settings
and the hash of the neutral evaluator checks file.
• Each task is run 3 times. We report mean ± SD and use a paired permutation test (α =
0.05) on the main metrics, which are Quality and Quality per 1,000 tokens.
9.7 Testing Strategy
• Unit tests for the router, the AST analyser (with a made-up cycle), the schema validator,
the adaptive stopper and the scorers.
• Integration test: one SIMPLE and one STRUCTURED task from start to end in the
sandbox.
• Fault tests: a broken UML and an incomplete user story must cause a retry and a rollback.
• A pilot with one task is run before the full batch of 300 runs.

9.8 Hardware and Execution
• A normal laptop or desktop with Docker is enough. No GPU is needed, because the
models are used through the API and the embedding model is small.
• Benchmark tasks run in parallel containers. The planning budget is about 10.8 million
tokens for the 300 core runs. We will replace it with the numbers measured in the pilot.
9.9 Limitations
• Most SRDD tasks may be routed as SIMPLE, so the UML and sprint steps may run less
often.
• The comparison with iCoder is indirect, because we use only its published results. The
direct comparison is with ChatDev.
• Only 20 tasks are used, so the statistical power is low. The embedding-based consistency
score is a weak way to measure correctness.
• The neutral evaluator uses only a smoke test for programs with a window, and hand-
written checks for some of the CLI and API tasks.
